# Architecture

Each merchant runs an independent deployment with its own environment, MySQL database, object-storage credentials/bucket and future payment accounts. One Java 21 Spring Boot modular monolith serves `/api/admin/**` and `/api/public/**`; React/Ant Design admin and Taro miniapp are separate clients. Flyway owns schema changes. Docker Compose starts MySQL 8.4, Redis 7.4, MinIO and Nginx for local use. Redis is reserved for cache/rate limits and never owns orders or stock.

Phase 1 modules: identity, store, catalog, supply and media. Admin authentication uses an opaque random bearer token; only its SHA-256 digest is persisted. The initial admin is created only when `ADMIN_INIT_PASSWORD` is supplied; no password is embedded in migrations. All admin routes are protected by Spring Security. Public catalog queries filter unpublished products and inactive SKUs in SQL. Media uploads use an `ObjectStorage` interface backed by MinIO, and image references are served through the backend so storage credentials remain private.

Phase 2 adds a separate consumer security principal. A consumer can hold multiple identities, but `(platform, app_id, platform_user_id)` is unique and identities are never merged merely because two platforms return similar data. The WeChat miniapp login sends a one-time code to the backend; the backend exchanges it with WeChat for an OpenID, keys the identity by the configured miniapp AppID, and issues its own opaque consumer session. The AppSecret is server-only. A unique-index conflict rolls back the losing consumer insert and reuses the committed identity. The development login is guarded by both configuration and active profiles: it is available only in `dev`/`test`, and enabling it with `prod` makes startup fail. Customer SQL always includes `consumer_id`; admin and customer sessions use distinct roles.

The authoritative sellable inventory is `supply_inventory` on a `sku_supply`. Each supply explicitly binds one supplier, one supplier-owned enabled shipping origin and one merchant-global shipping template. Phase 2 checkout always selects the SKU's single default supply, so there is no competing SKU-level stock count and no automatic warehouse selection. `on_hand_qty - reserved_qty` is available stock. Reservation uses an atomic MySQL conditional update inside the same transaction as the order, snapshots and stock ledger; Redis is not authoritative. Cancellation and timeout transition the order only from `PENDING_PAYMENT`, then conditionally change each reservation from `HELD` to `RELEASED`, making repeated and multi-instance scans safe.

Shipping is mainland-China-only and uses grams. `net_weight_g` is display weight; `billable_weight_g` is the per-unit carrier charge weight. Items sharing supplier, shipping origin and the supply-level template form one fulfillment group and their billable weights are summed; different groups are quoted separately. Product-production origin is stored separately on the product. Rules match district, then city, province, then `000000`. No match means not deliverable. A matched blocked rule is evaluated before free shipping and can never be overridden by it. Otherwise the first-weight fee applies and any positive remainder is rounded up by `ceil(remainder / step_weight_g)`. Free shipping is a per-group merchandise threshold; there is no hard-coded nationwide free shipping.

Checkout re-quotes server-owned prices, status, default supply, stock and shipping. A changed quote returns `QUOTE_CHANGED` rather than silently placing the order. An idempotency key is unique per consumer and bound to the normalized cart/address/quote request. Orders snapshot address, item/SKU price and weight, supply identifiers, supplier/origin labels, matched region, template version/name, group amount and shipping fee. Later catalog, address or template edits cannot rewrite history. No fulfillment task or supplier notification is created before a future verified payment.

Money remains integer fen in persistence and APIs. Phase 3 introduces replaceable create/query/close/verify-and-parse payment adapters. The development simulator is enabled only by an explicit flag under `dev`/`test`; a production profile rejects it at startup. Unconfigured WeChat/Alipay adapters return unavailable and never fall back to simulation. Payment order, attempt, channel event and anomaly tables are separate from sales-order and fulfillment states.

Payment confirmation serializes on sales order then payment attempt (the same order used by close coordination), validates amount/currency/merchant subject, and deduplicates channel events. Reservations convert from `HELD` to `SOLD` by decrementing on-hand and reserved together. Checkout-time order groups—not current catalog defaults—produce uniquely constrained fulfillment tasks, task items and identifier-only notification outbox rows in the same transaction. External create/query/close calls stay outside database transactions.

Supplier sessions are a third principal type. Supplier SQL is always scoped by the bound `supplier_id`; only an administrator can create, disable, rebind or reset an account. Parcel creation locks the task and ordered task items, uses a per-task idempotency key, and updates shipped counters conditionally within one transaction. The outbox worker uses conditional leases for concurrent claim/crash recovery and exponential retry. Its current adapter is an in-process development reminder; SMS and platform subscription messages are explicitly not connected.

Phase 4 keeps event receipt durable and separate from state mutation. Verified payment/refund payloads are persisted
before processing; recovery schedulers replay `RECEIVED` rows after crashes. After-sales, original fulfillment and
replacement fulfillment use the same order-first lock discipline. Private evidence objects have dedicated ownership
metadata and authenticated download routes and are never exposed through the public product-media endpoint.

Settlement is an append-oriented accounting subdomain, not a payment splitter. It snapshots supply price at checkout,
records goods/freight/deductions/replacement costs independently, locks entries into statements through unique
constraints, and only records human-entered payments and reversals. No bank transfer or supplier payout API exists.

Version choices are intentionally conservative and compatible: Spring Boot 3.4.5 (Java 21 compatible), MySQL 8.4 LTS, Redis 7.4, MinIO RELEASE.2025-04-22T22-12-26Z, React 18.3.1, Ant Design 5.24.9, Vite 6.3.4, Taro 4.0.9, TypeScript 5.8.3. Pin changes only after checking both miniapp targets and backend builds.

Customer address selection and validation use the same backend classpath region catalog, exposed at `/api/public/regions`. The catalog is a normalized six-digit province/city/district hierarchy; address writes accept codes and resolve names on the server. It is independent of shipping availability: valid addresses can be saved, while checkout quotes decide whether a shipping rule serves them. Existing addresses whose codes are absent from the catalog require explicit reselection when edited. The catalog snapshot derives from [Administrative-divisions-of-China 2023 pca-code data](https://github.com/modood/Administrative-divisions-of-China/blob/master/dist/pca-code.json) (WTFPL); province and city codes were padded to six digits, and direct-administered `市辖区` display labels use their province names. Review the snapshot when administrative boundaries change.
